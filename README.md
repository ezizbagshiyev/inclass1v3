## Reflection

The biggest surprise was seeing how the widget tree actually responds when the app’s state changes. Before this activity, I thought I had to manually change the whole screen. I learned that Flutter rebuilds only the parts of the widget tree that need to update.

The concept that took me the longest to understand was the difference between stateless and stateful widgets. It started to make sense when I connected it to the app: a stateless widget displays information that stays the same, while a stateful widget can remember changes, like the selected tab. Seeing `setState()` update the screen helped me understand how it works in practice.

The GitHub part that felt least familiar was knowing when to commit, push, and create a pull request. I worked through it by following each step carefully and checking GitHub after every action. I eventually understood that commits are saved checkpoints, while pull requests let other people review proposed changes.

If I rebuilt this activity tomorrow, I would plan out the widget tree before starting and make smaller commits throughout the process. I would also test the state and lifecycle methods earlier so I could understand what each part was doing instead of trying to figure everything out at the end.
